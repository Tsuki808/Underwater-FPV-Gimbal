# 联调问题排查记录

本文档整理控制中间件开发与现场联调过程中实际遇到的问题及定位结论，供后续复用参考。

## 1. 串口打开失败：错误代码 2

**现象**

```
❌ 串口 COM13 打开失败! 错误代码: 2
```

同时扫描到本机存在 `COM4`、`COM5`，但目标 `COM13` 不存在。

**定位**

错误代码 2 为 `ERROR_FILE_NOT_FOUND`，即系统无此串口设备。根本原因是现场并未使用 USB-TTL 直连，而是通过**串口转网口模块**接入。程序却在按串口方式打开设备。

**结论**

`192.168.1.50` 可 `ping` 通，说明该 IP 为网络可达的串口服务器。控制链路应从串口直连改为 TCP 网络透传。

**教训**

出现 `ERROR_FILE_NOT_FOUND` 时应先确认物理接线方式，而非反复更换 COM 号。

---

## 2. TCP 连接失败：错误代码 10061

**现象**

第一次改为 TCP 后，尝试连接 `192.168.1.50:4019` 之外的其他端口时报：

```
❌ 连接失败! 错误代码: 10061
```

**定位**

`10061` 为 `WSAECONNREFUSED`，表示目标主机可达但该端口无服务监听。属于**端口号不匹配**，而非网络不通。

**结论**

串口服务器的监听端口需从设备配置页面确认。源码中最终固化为 TCP `4019`。为便于排查，`udp_test.cpp` 提供了常见端口批量探测能力。

---

## 3. 链路模式误判（TCP ↔ UDP）

**过程**

排查过程中曾一度将输出链路改为 UDP（`sendto`），依据是"不需要端口号后缀"的错误理解。实际设备配置为 **TCP Server** 模式。

**结论**

串口服务器通常支持 TCP Server / TCP Client / UDP 多种透传模式，**必须与设备实际配置一致**。判定依据应由设备配置界面决定，不能凭现象推测。

---

## 4. 云台收到指令但不动（协议层问题）

**现象**

TCP 连接已正常建立、指令持续下发，但云台无动作。

**定位**

对照协议文档逐字段比对 Python 与 C++ 实现，发现三处偏差：

1. **`cmd` 字节未按位域构造**：早期 C++ 版本直接写 `0x04` / `0x02`，未显式表达 `trig[3 位] + valu[5 位]` 结构。数值虽恰好相同，但缺少字段语义，后续修改易出错。
2. **Pitch 未取反**：Python 工作版本中 `PITCH_INVERT = -1`，即 `int16_t(-pitch * 100)`。C++ 版本初期漏掉了反向修正。
3. **`aux` 字节未显式初始化**：启动帧中该字段位置未明确置零。

**结论**

按 Python 工作版本的实现逐项对齐后，云台恢复响应。核心修正为 Pitch 取反与 `cmd` 位域构造。

---

## 5. 重复包导致指令风暴

**现象**

OpenTrack 的输出并非严格按帧率等间隔推送，存在短时间内重复发送同一姿态样本的情况。

**结论**

在收包后增加去重逻辑：C++ 版比对 `yaw`/`pitch` 数值，Python 版比对整包哈希。重复样本直接 `continue`，不进入发送队列。

---

## 6. 排查方法总结

| 手段 | 用途 |
|------|------|
| `ping 192.168.1.50` | 确认串口服务器网络可达 |
| 错误码判定 | `2`=设备不存在，`10061`=端口无服务，据此区分物理层与配置层问题 |
| `udp_test.cpp` | 批量探测串口服务器监听端口 |
| 首帧十六进制打印 | 与协议文档逐字节比对，定位字段级偏差 |
| Python ↔ C++ 交叉对照 | 两套独立实现互为参照，快速暴露单侧实现错误 |

排查顺序建议：**物理接线 → 网络可达 → 端口可达 → 链路模式 → 协议字段 → 数据流净化**。
