# 控制中间件设计说明

## 1. 设计目标

在 VR 头部追踪（UDP）与工业串口云台（TCP/RS485）之间构建一条**低延迟、稳定**的桥接链路。核心约束：

1. 控制回路的软件引入延迟必须尽可能小，避免叠加到本就存在的网络与机械延迟之上。
2. 输入侧（OpenTrack）存在重复包与传感器抖动，输出侧必须做净化。
3. 需要兼容两种现场接线方式：USB-TTL 直连串口、串口转网口模块（TCP）。

## 2. 分层结构

```
┌──────────────────────────────────────────────────────────┐
│ 输入层    UDP Receiver                                   │
│           bind 0.0.0.0:4242 / 127.0.0.1:4242            │
│           校验包长 == 48，解出 Yaw / Pitch / Roll         │
├──────────────────────────────────────────────────────────┤
│ 处理层    Dedup → Filter → Predict → Deadzone            │
│           整包哈希去重 / 一维卡尔曼 / 速度外推 / 死区      │
├──────────────────────────────────────────────────────────┤
│ 编码层    PacketBuilder                                  │
│           角度 ×100 → int16，Pitch 取反，填充固定字段      │
│           计算 CRC-16 → 大端写入偏移 38                   │
├──────────────────────────────────────────────────────────┤
│ 发送层    AsyncSerialManager / 直发 Socket               │
│           TCP 或串口，独立线程 + 有界队列（上限 10）        │
└──────────────────────────────────────────────────────────┘
```

## 3. 关键设计决策

### 3.1 为何使用 C++ 原生 Socket

原方案使用脚本语言实现，受运行时垃圾回收影响会产生不可预期的停顿。改用 C++ + WinSock2 后，数据解包、角度处理与协议封装全部在栈上完成，无动态分配，实测单帧软件处理耗时小于 1 ms。

### 3.2 二进制定长协议

相较 JSON / XML 等文本协议，40 字节定长二进制帧显著降低了传输带宽与编解码开销，同时使接收端可以按固定偏移直接取值。代价是字段含义必须靠文档维护（见 `protocol.md`）。

### 3.3 去重的必要性

OpenTrack 存在"爆发式发送"行为：同一姿态样本可能在极短时间内重复推送多次。若不去重，云台会收到大量等价指令，既浪费带宽也加剧机械动作。C++ 版比对 `yaw`/`pitch` 浮点值是否变化；Python 版对整包做哈希比对。

### 3.4 预测与滤波的取舍

- **卡尔曼滤波**抑制传感器噪声，但滤波越强、相位滞后越大。
- **运动预测**基于最近帧速度外推，补偿链路延迟，但速度估计错误时会产生过冲。
- 二者配合通过 `SMOOTHING_FACTOR`、`PREDICTION_MS` 调节，并按场景预设三档（`turbo` / `balanced` / `smooth`）。

### 3.5 有界发送队列

发送队列上限为 10 帧。当消费速度跟不上生产速度时，**丢弃新包而非排队**——控制链路中旧数据的价值高于延迟数据，堆积只会放大滞后。

### 3.6 非阻塞 I/O

C++ 版对 UDP 接收套接字设置 `SO_RCVTIMEO = 100 ms`，超时即视为正常空闲（`WSAETIMEDOUT` 不打印日志），避免主循环被阻塞。Python 版对 UDP 套接字设置 `settimeout(0.1)` 并捕获 `socket.timeout`。

## 4. 两份 C++ 实现的差异

| 项目 | `ultra_low_latency.cpp`（当前） | `backup` 早期版本 |
|------|--------------------------------|-------------------|
| 输出链路 | TCP → 串口服务器 | 串口直连 `COM13` |
| 地址配置 | `#define` 宏，集中于文件顶部 | 硬编码于 `main` |
| 工作模式 | `WORK_MODE` 宏（默认 Follow） | 硬编码 FPV |
| 控制字节 | 按位构造，字段语义显式 | 直接写数值 `(2 << 2)` |
| Pitch 处理 | 取反 | 未取反 |
| 调试输出 | 打印首帧完整十六进制 + 帧结构说明 | 仅打印实时角度 |
| 时间测量 | `QueryPerformanceCounter` | 无 |

当前版本为联调后的最终形态。早期版本未纳入仓库，其差异仅在此处记录以供对照。

## 5. Python 两份实现的差异

| 项目 | `gimbal_controller_ultimate.py` | `gimbal_controller.py` |
|------|----------------------------------|------------------------|
| 定位 | 功能完整版 | 协议验证基础版 |
| 连接方式 | TCP / 串口二选一（`USE_TCP`） | 仅串口直连 |
| 发送方式 | 独立线程异步队列 | 主循环同步 `write` |
| 数据处理 | 去重 + 卡尔曼 + 预测 + 死区 | 无 |
| 控制频率 | 可配置（100–150 Hz） | 固定 10 ms 周期 |
| 参数单位 | 集中 `Config` 类 + 命令行参数 | 常量散落 |
| 性能监控 | FPS / 延迟统计 | 无 |
| 协议实现 | `PacketBuilder` 零拷贝原地修改 | 每帧重新构造 `bytearray` |

两者共享同一套 CRC 算法与控制字节语义，可交叉验证协议实现正确性。

## 6. 延迟构成

端到端延迟（Motion-to-Photon）由以下部分串联：

```
OpenTrack 姿态解算 → [UDP 传输] → 中间件处理 → [TCP 传输 + 串口透传]
   → 云台 PID 响应 → 机械动作 → 摄像头成像 → 图传回传 → 头显显示
```

中间件本身仅占其中"处理 + 封装"一段。源码中通过 `QueryPerformanceCounter` 测量收包到发包的耗时，用于确认该段不构成瓶颈。其余环节属于网络、固件与机械范畴，不在本中间件的优化范围内。
